Plan leaks fork/heredoc - Minishell

Diagnostic et TODO avant de modifier le code. Objectif choisi : ne plus avoir de still reachable dans les enfants forkes, pas seulement zero definitely lost.

Etat actuel

Le log Valgrind du cas heredoc montre :

definitely lost: 0 bytes in 0 blocks

still reachable: 5,846 bytes in 201 blocks

Donc ce n'est pas une fuite perdue, mais le standard voulu maintenant est plus strict : supprimer aussi le still reachable venant de notre code.

Pourquoi ca arrive

Les enfants crees avec fork() heritent d'une copie de la memoire du shell parent : env, tokens, commandes parsees, ligne courante, etc. Si l'enfant fait juste exit(status), il quitte sans nettoyer cette copie. Valgrind voit alors cette memoire comme encore accessible (still reachable).

Dans le cas heredoc teste :

cat << $USER
nvlknwvl
vbkwebne
$USER

Les stacks Valgrind visibles dans ton log pointent vers :

  • cpy_key, cpy_value, new_env_node : environnement herite du parent.
  • create_token_node, add_word_token, add_operator_token : tokens de la commande heredoc.
  • create_cmd_node, create_cmd_and_args : commande en cours.
  • expand_word : expansion du delimiter $USER.
  • read_input, add_char_to_line : lignes lues pendant heredoc.

Piege important

ImportantDans heredoc, le t_cmd *cmd local n'est pas encore forcement accroche dans shell->cmds.

Le chemin actuel est :

process_line()
  parse_tokens(shell->token, shell->env)
    create_cmd_node(tokens, env)
      open_redirections(cmd, tokens, env)
        open_heredoc_redirection(cmd, delimiter, env)
          fork()
          heredoc_child(pipefd, delimiter, env)
            exit(res)

Comme le heredoc se fait pendant la creation du cmd, un cleanup enfant qui nettoie seulement shell->cmds peut rater le cmd local. Il faut donc prevoir un parametre optionnel local_cmd.

Conclusion precise depuis ces stacks : les allocations restantes ne viennent pas d'un malloc perdu au milieu du heredoc. Elles correspondent a des objets normaux du shell parent, visibles dans l'enfant parce que l'enfant heredoc fait exit(res) sans nettoyage complet.

Comment on deduit que c'est l'enfant heredoc

  1. La commande testee est cat << $USER, donc elle passe par open_heredoc_redirection.
  2. open_heredoc_redirection appelle fork().
  3. Dans l'enfant, heredoc_child lit les lignes puis fait actuellement exit(res).
  4. Le process enfant a une copie memoire de env, tokens, cmd et ligne courante, car fork duplique l'espace memoire du parent.
  5. Les stacks Valgrind montrent exactement ces familles : setup_env, tokenizer, parse_tokens, expand_tokens.
  6. Le resume final dit definitely lost: 0 et possibly lost: 0, donc les pointeurs existent encore ; ils n'ont juste pas ete liberes avant la sortie de l'enfant.

Design propose

Nouvelle fonction

void clean_child_exit(t_shell *shell, t_cmd *local_cmd, int status);

Role : nettoyer la copie memoire de l'enfant avant exit(status).

void clean_child_exit(t_shell *shell, t_cmd *local_cmd, int status)
{
    if (local_cmd && local_cmd != shell->cmds)
        free_cmds(local_cmd);
    free(shell->current_line);
    shell->current_line = NULL;
    free_cmds(shell->cmds);
    free_tokens(shell->token);
    free_lst_env(shell->env);
    clear_history();
    exit(status);
}

Le parametre local_cmd sert surtout a heredoc, parce que le cmd peut exister localement sans etre encore dans shell->cmds.

Decision technique

A retenirLe probleme n'est pas readline dans ce log : readline est deja largement supprime par suppressions. Le reste vient surtout de notre memoire heritee dans les enfants forkes.

AttentionNe pas remplacer tous les exit() au marteau. Certains sont dans le parent (clean_exit), d'autres sont dans des enfants, et ceux d'exec externe court-circuitent le cleanup.

Approche saineTraiter un type d'enfant a la fois : heredoc, puis pipeline, puis exec externe.
